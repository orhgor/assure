# Pi ↔ OMP integration — design

Status: design only. No code, no config, no deploy is proposed as done here. Every statement below traces to a Phase 1 finding (A1 Pi surface, A2 OMP contract, A3 doc drift, A4 OMP isolation); evidence classes are `CODE` (file:line), `SSM` (read-only commands on `i-03e39eccc57572191`) and `HTTP`.

Naming, fixed for this document: **OMP** = Open Memory Protocol, the app-side memory server at `:3456` (`omp.service`, npm `omp-server`). **Pi** = Oh My Pi, the coding agent (executable `omp`, package `@oh-my-pi/pi-coding-agent`). The directory `~/.omp/` is a collision: on the box it is **OMP's** data dir (`api_key` + `omp.db*` only), on the developer Mac it is **Pi's** home *and* the Mac's local OMP server dir (A1 naming trap; A2.7; A4 terminology note).

## What OMP is

OMP is the app's memory service, chosen as the package `omp-server` 0.2.0 (Apache-2.0, repo `github.com/SMJAI/open-memory-protocol`, packages/server; deps `express ^4.18.3` + `zod ^3.22.4`; engines node >=22.5.0) (A2.7). On the staging box it is exactly one systemd unit: `omp.service`, `User=ubuntu`, `Restart=on-failure`, `RestartSec=5`, `Environment=OMP_API_KEY=<redacted: 64 hex chars>`, `OMP_DB_PATH=/home/ubuntu/.omp/omp.db`, `OMP_PORT=3456`, `ExecStart=/opt/node-v24.11.1-linux-arm64/bin/node …/omp-server/dist/index.js` (SSM `systemctl cat omp.service`, A2.7). Those three environment variables are the entire configuration surface (`index.js:12-14`, A4.5).

Storage is Node's built-in SQLite (`node:sqlite` `DatabaseSync`) on `/home/ubuntu/.omp/omp.db` (2 797 568 B + WAL 4 293 072 B at probe time), `journal_mode WAL`, with **one** table `memories`, one FTS5 virtual table `memories_fts(content, tags, external content, content_rowid=rowid)` kept in sync by three triggers (`ai`/`ad`/`au`), and indexes on `type`, `namespace`, `source_tool` (A2.2, A2.7, A4.2). There are no collections: the only grouping primitives are the nullable `namespace` string and the JSON `tags` array (A2.4).

HTTP surface: express with `express.json({limit:'1mb'})`; bearer auth on every path **except** `/v1/health`, which is unauthenticated by design (`index.js` auth middleware returns `next()` for `req.path === '/v1/health'`); unknown paths answer `404 {"error":"not_found"}` (A2 endpoint table, A2.7). Live state today: `1160` rows, every row `source_tool='assure'`, every row `namespace='project:prompt-matrix'`, every row `type='semantic'`, `expires_at` null, 58 rows containing `jdf_chunk` (A2.2, A2.7, A3 §0, A4.2). Health reports `"version":"0.1"` hardcoded in `index.js` while `package.json` says `0.2.0` — the health version string is not the package version (A2.7).

Reachability: `:3456` binds all interfaces (`LISTEN *:3456`) but there is no cloudflared ingress for it (only `staging.`/`prototype.` → `http://localhost:8891`), the security group `sg-006d2cd5bc7c3877c` permits only tcp/8891, `ufw` is inactive, and an external `curl http://3.237.106.38:3456/v1/health` returned `http_000` — so OMP is reachable only from the box/VPC, while remaining reachable from anything on the same subnet (A2.7, A4.5 §7).

## What Pi is

Pi is the coding agent installed **on the developer workstation only**: package `@oh-my-pi/pi-coding-agent`, executable `omp`, active profile `assure` (env `OMP_PROFILE=assure`, `PI_PROFILE=assure`, `PI_CODING_AGENT_DIR=/Users/og/.omp/profiles/assure/agent`), config `~/.omp/profiles/assure/agent/config.yml` (210 bytes; only `modelRoles`, `symbolPreset`, `composer`, `theme`, `setupVersion`, `task`) (A1 paths/requested commands, A1.4). On the box Pi is **not installed**: `which omp omp-mcp` is empty, there is no `profiles/` or `agent/` under `/home/ubuntu/.omp`, and the global node_modules holds only `@uurtech, corepack, npm, omp-server` (A1 §6, A2.7).

Pi's model of a working session is a JSONL file under `<agentDir>/sessions/<encoded-cwd>/<timestamp>_<sessionId>.jsonl`, physically starting with a fixed-width 256-byte title slot, then a version-3 session header (`version, id, timestamp, cwd, title, titleSource, additionalDirectories, previousSessionFiles, providerPromptCacheKey, parentSession`) followed by append-only entries carrying `id`/`parentId` with a movable `leafId` pointer; sessions are bucketed per canonicalized cwd (A1.5). Side indexes: per-scope `recent-sessions.jsonl` and SQLite `history.db` (`history`, `session_titles`, `history_fts`) (A1.5).

Pi ships a native memory subsystem that is **switched off**: `memory.backend` is an enum — `off` (default), `local`, `hindsight`, `mnemopi`, `sharpshooter` (`settings-schema.ts:3167-3179`) — and the effective values are `memory.backend = off`, `memories.enabled = false`, `autolearn.enabled = false`, with none of those keys present in the installed `config.yml` (A1.6). Pi contains **zero OMP integration**: greps for `Open Memory Protocol`, `omp-mcp`, `omp_remember`/`omp_recall`, `OMP_API_KEY`/`OMP_SERVER`/`OMP_DB_PATH`/`OMP_PORT`, `localhost:3456` across the Pi packages return no hits (A1 naming trap/contradictions; independently, a grep of `@oh-my-pi/pi-coding-agent`, `pi-mnemopi`, `pi-agent-core` for `OMP_SERVER|localhost:3456|omp-mcp|memories/search|open-memory-protocol` returned zero hits, A4.2). Any Pi→OMP link is therefore a **new integration**, never a current behaviour (A4.2).

## What A2 established about OMP's API

Five calls exist in the app's client and no more: `GET /v1/health`, `POST /v1/memories`, `POST /v1/memories/search`, `GET /v1/memories`, `DELETE /v1/memories/{id}` (`prompt_matrix/omp_client.py:119,134,213,234,253`); the base URL is `OMP_SERVER`, defaulting to `http://localhost:3456` (`omp_client.py:19`), and the key comes from `~/.omp/api_key` — **the file wins whenever it exists**; `OMP_API_KEY` is only the `FileNotFoundError` fallback (`omp_client.py:20,44-51`) (A2.1, A2.7, A4 corrections). The same code also drives the browser-facing proxies `POST /api/omp/remember`, `GET /api/omp/recall`, `GET /api/omp/memories` (`routers/omp_routes.py:14-45`), which are *not* OMP endpoints (A2 proxy table).

A memory record is one row of table `memories`, serialised by `rowToMemory()`: `id` (PK, server-generated `mem_` + 16 chars of `[a-z0-9]`), `content` (NOT NULL; server accepts 1..10000; the client truncates at 9000 + `…`), `type` (CHECK IN `episodic`|`semantic`|`procedural`), `source_tool` (NOT NULL), `source_session_id`, `source_user_id`, `source_timestamp` (NOT NULL), `tags` (JSON array of strings, NOT NULL default `[]`), `namespace` (nullable), `created_at`, `updated_at`, `expires_at` (nullable), `metadata` (JSON, default `{}`). The JSON a caller sees is `id, content, type, source{tool,session_id,user_id,timestamp}, tags, namespace, created_at, updated_at, expires_at, metadata`; a live `GET /v1/memories?limit=1` confirmed exactly those ten keys, with `source={'tool':'assure','timestamp':'2026-09-17T19:20:24Z'}`, `expires_at=null`, `metadata='{}'` (A2.2).

What can scope a read, and what cannot (A2.4, A4.1, A4.4):

| Field | Filter in SQL (list / search) | Notes |
|---|---|---|
| `namespace` | yes / yes (`sqlite.js:115-118`, `:164`) | nullable string, `^[a-z0-9_:\-]+$`, max 100 (`types.js:17`); a **filter the reader may apply, not an access boundary** — any valid key reads any namespace (A4.4) |
| `type` | yes / yes (`sqlite.js:107-110`, `:163`) | the only other server-side retrieval filter |
| `tags` | list only, **after** LIMIT/OFFSET, `every()` + exact equality (`sqlite.js:127-129`); accepted by the search schema and **ignored** by `storage.search` (`types.js:27` vs `sqlite.js:159-181`) | app tags: `vault` 532, `default` 391, `prj_yhr-5cbgb_7e` 386, `ast` 362, `redhat` 162, `redhat:…` 136, `refine` 46 (live census) |
| `source.tool` | list only (`sqlite.js:111-114`); **no** search filter; no `tool` parameter in `omp_list_memories` | 100% of live rows are `assure` |
| `key` (the app's `ast:…`, `jdf:…`) | **not a server concept** | write-side tag (truncated to 50 chars, `omp_client.py:93-108`) + read-side FTS query string (A2.3) |
| `metadata`, `source_session_id`, `source_user_id` | no filter at all | — |

Other measured API behaviour: `mode` is accepted and ignored — `storage.search` hard-codes keyword FTS and always reports `mode_used: 'keyword'`, and `list.sort` is destructured and unused (A2.4, A4 corrections). The recall window is the `limit` of `/v1/memories/search`: `1..100, default 10` (`types.js` `SearchMemoriesSchema`; `types.ts:31`), the maximum confirmed live (`limit 200` → **422**); there is no offset, page, time-window or recency parameter, and because ranking is FTS5 over `content`+`tags` of the whole store with each whitespace-separated word quoted and OR'd, the window is a **ranking window, not a filter** (`omp_client.py:136-138`) (A2.5). Failure modes are flat: `HTTPError` → parsed body + `error` + int status (`401 unauthorized`, `422 validation_error`); transport error → `{"error": str}` with **no** status; empty body/204 → `{"ok": true, "status": 204}`; and `safe_omp_remember`/`safe_omp_recall` collapse every one of those into `None`, while `omp_delete_memory` collapses 404 and network failure into `False` (`omp_client.py:78-90,186-193,201-210,247-250`) (A2.6). The only status-preserving surface is the Flask `POST /api/omp/remember` (201 on id, else the int status when >= 400, else 502) — and its only caller discards the response (`static/substrate_vault.js:400-409`) (A2.6).

Box facts that constrain any integration: `/v1/health` is 200 unauthenticated while an unauthenticated `GET /v1/memories` is 401; the key file (`/home/ubuntu/.omp/api_key`, 65 bytes, mode 600) has the same sha256 prefix `5a67cea2…` as the unit's `OMP_API_KEY`, so the app reads from disk and the service holds the same secret; `/v1/extract` and `/v1/compress` answer `422 no_api_key` because the unit has no `OMP_AI_API_KEY`; endpoints present but never called by the app are `GET`/`PUT /v1/memories/{id}`, `POST /v1/extract`, `POST /v1/compress`, `GET /v1/export`, `POST /v1/import` (A2 endpoint table, A2.7).

## A4's isolation verdict

**"Cannot share the instance safely as it stands today."** Three independent counts, each reproduced (A4 verdict):

1. The app's cache/context reads are unscoped, so another writer's row can be returned as the app's own data. Reproduced end to end: `safe_omp_recall(redhat_cache_key(project_id))` → `_best_memory_content` → the plain-string branch → `load_redhat_critique` → `run_redhat_audit(previous_context=…)` → inserted at the front of the Red-Hat prompt (up to 4000 chars). On the throwaway instance the foreign row ranked first and `safe_omp_recall("redhat:default")` returned exactly `'Session note: the redhat default persona pass was run; liability limit confirmed.'` — model input, therefore a prompt-injection surface, not just noise (A4 Counter-example A).
2. The credential is one bearer key with no scoping: the same key that stores also lists everything, reads by id, patches by id and deletes by id (`index.js:19-31`, `routes/memories.js:34-54`). Reproduced: `omp_delete_memory(<foreign id>)` returned `True` (A4 verdict #2, Counter-example D).
3. Isolation is not merely unused, it is unavailable below the whole instance: `namespace` is a filter the reader may choose to apply (`sqlite.js:164`), and the app's read path never applies it (`omp_client.py:141-146` has no namespace parameter) (A4 verdict #3, A4.3, A4.4).

Reproduced crowding: on the box a direct FTS query for `"liability" OR "limit"` returned five `PEM_CACHE_V1` AST blobs as the top five rows, and on the throwaway instance `omp_recall("liability limit", 10)` with two app chunk rows and two foreign rows returned foreign, foreign, app chunk, app chunk (A4 Counter-example C). Chunk *retrieval* survives today only because the app probes each ingested document's own tag (15 durable `jdf_cli_documents` rows == 15 distinct OMP chunk `(tenant, doc)` pairs) — the cache path (limit 10) has no probe at all (A4 Counter-example C). The app's real tenant scoping is a payload check *after* the search (`jdf_memory.py:332-350`), and the app-side tag filter used by the compliance UI is broken end to end — it queries `tags=project:<pid>` while no writer stores a `project:`-prefixed tag (live: `n=0` with `total=1160`) (A2.4).

A4's conditions for sharing to become safe — all three, and nothing less: scope every app search by namespace and give the second writer its own namespace; remove or guard the first-row fallback in `_best_memory_content` (`omp_client.py:172-181`); give the second writer its own credential, which `omp-server` 0.2.0 cannot express, so in practice this means **a second instance** (A4 verdict).

## Proposed integration

Design only; nothing below is implemented, and no step is proposed as done.

**Where Pi would read from OMP at session start.** The only Pi-side points that can place text in front of the model before work begins are the hook events `session_start` (`types.ts:481`) and `before_agent_start` (`:498`, which may inject a message or override the system prompt) — or, equivalently, an extension registered via `registerTool`/`pi.on` on the same events (A1.1, A1.2). A read at session start means one `POST /v1/memories/search` carrying an explicit `namespace` (the app's client does not do this today — `omp_client.py:141-146` — so the Pi-side client must), with `limit` inside `1..100` (A2.5). Nothing in Phase 1 shows a hook firing, so this read point is a design choice on top of an unexercised mechanism, not a measured capability (A1.1).

**Where Pi would write at session end.** `session_shutdown` (`types.ts:492`), with `session_stop` (`extensions/types.ts:1292`) as the extension-side equivalent; one `POST /v1/memories` per session summary (A1.1, A1 tail citations, A2 endpoint table). No periodic writes and no per-tool writes: each write competes for the same FTS window that A4 measured as already contested (A4 Counter-example C).

**Schema of a Pi session memory.** The record fields are fixed by OMP (A2.2); the payload below is the design.

| Record field | Value | Why |
|---|---|---|
| `content` | JSON text, following the app's own precedent of nesting JSON inside `content` (`jdf_memory.py:405-417`): `kind:"pi_session"`, `agent:"pi"`, `profile`, `session_id`, `cwd`, `project`, `started_at`, `ended_at`, `summary`, `decisions[]`, `files[]`, `open_questions[]` | `content` is the only free-text field; nesting JSON is the pattern already in the store (A2.2) |
| `type` | `"episodic"` | the CHECK allows `episodic`/`semantic`/`procedural` (A2.2); every live row is `semantic`, and `type` **is** a server-side search filter, so a Pi row is filterable without touching the app's rows (A2.4) |
| `namespace` | the second instance's own namespace, e.g. `agent:pi` | matches `^[a-z0-9_:\-]+$`, max 100 (`types.js:17`); the only field besides `type` that can scope a search (A4.4) |
| `tags` | `["pi", "pi:<profile>", "pi_session:<session-id-prefix>"]` | tags are descriptive only: search ignores them, and list applies them after pagination (A2.4) — so keep them ≤ 20 entries and ≤ 50 chars each (A2 endpoint table) |
| `source` | `{tool:"pi", timestamp:"<ISO8601 Z>"}` | `source_tool` is recorded and list-filterable; the box's rows are all `assure` today (A2.2, A2.4) |
| `metadata` | `{}` | nothing can filter on it (A2.4) |
| `expires_at` | `null` | every live row is null; any retention policy is a decision this evidence does not settle (A2.2) |

**Isolation mechanism.** A **separate OMP instance**, per A4's third condition: its own systemd unit on `:3457`, its own `OMP_DB_PATH`, its own `OMP_API_KEY`, loopback/box-local only. A namespace alone is not sufficient, because a namespace is a reader-side filter (A4.4) and one key owns every row in an instance (A4 verdict #2). If Pi's rows ever had to live in the app's instance, all three A4 conditions are prerequisites and none holds today.

**Pi-side wiring.** Pi has no OMP client, so the link is either (a) an MCP server entry in the profile's native config `<agentDir>/mcp.json` — absent today (A1.3) — pointing at an OMP MCP adapter; the workstation already has such an adapter defined but opted out (`omp` → `/Users/og/.omp/mcp.sh`, a 0.2.0 `omp-mcp` bridge with tools `omp_remember`, `omp_recall`, `omp_forget`, `omp_list`, `omp_extract`, `omp_compress`), which would need `enabledProviders` to include the source and `OMP_SERVER` to point at the Pi instance; or (b) a small extension using `registerTool` + `pi.on('session_start'|'session_shutdown')` (A1.3, A1 naming trap, A1.2). Both are Pi-side artefacts that do not exist yet.

**Cost of the recommended shape** (A4.5, measured): one new unit file modelled on `omp.service` with `OMP_PORT=3457`, `OMP_DB_PATH=/home/ubuntu/.omp-pi/omp.db` and a fresh 64-hex key written to that dir's `api_key` with mode 600 (A4.5 step 2), a `~/.omp-pi` dir owned by `ubuntu`, and `systemctl daemon-reload && systemctl enable --now`. Footprint: ~70–80 MB RAM (the existing instance is RSS 68 MB / cgroup 78.3 MB) and a few MB of disk, against a `t4g.small` with 1835 MB RAM (1016 MB available) and 33 GB free of 48 GB. No security-group change is needed (`:3457` is not internet-reachable; the SG already allows only 8891), but `app.listen(PORT)` binds all interfaces (`index.js:63`), so `:3457` is reachable from anything on the same subnet unless a dist patch or an nftables/iptables rule is added. Consequences to accept: two stores to back up (no backup script references `/home/ubuntu/.omp` today), no `MemoryMax` on either unit, and — if the *app* were ever to move instances — a code change at `omp_client.py:20`, because the key path is hard-coded and `OMP_API_KEY` only applies when the file is missing (A4.5).

## What is required before implementation

- **Pi side — a client, because none exists.** Pi ships no OMP integration at all (zero grep hits across `@oh-my-pi/pi-coding-agent`, `pi-mnemopi`, `pi-agent-core`, A4.2; A1 contradictions). Two gaps to close: (a) a client that speaks OMP's REST surface — the shipped `omp-mcp` 0.2.0 adapter writes `namespace: args.namespace ?? null` and `source.tool` hardcoded to `claude` (`omp-mcp dist/index.js:114,116`), so it must be handed an explicit namespace and corrected tool label, or bypassed; (b) Pi's own hooks/extensions are the interception points but nothing is installed — `hooks: 0`, `extension-modules: 0`, `extensions: []` — and hook *firing* was never observed in Phase 1 (A1.1, A1.4). Whether an upstream change is needed depends on (a): if the adapter is patched locally, that is a fork of a third-party package; if not, it is configuration only. Phase 1 does not establish which, so **not determinable from evidence** — what would answer it: reading `omp-mcp`'s accept/response contract against a live server with a namespace argument.
- **OMP side — credentials, not namespaces.** OMP has no collection concept and no per-writer identity: one bearer key authorises every route (`index.js:19-31`), and `namespace` is a label with a reader-side filter (A4.4). Adding per-writer keys or enforced namespaces is an upstream change to `omp-server` (published package, not vendored); without it, the isolation mechanism must be a second instance. Also do not design on `search.tags`, `mode`, or `list.sort`: all three are accepted and ignored in this build (A2.4).
- **Operational prerequisites.** A deploy path that works with a read-only box key and no docker (fetch + checkout + unit restart; A3 §0, A3.2 §5); a backup decision for the new store (none exists today, A4.5 §8); a `MemoryMax` decision for both units; and a retention policy for `expires_at`, which is `null` on every row today and is not settled by any Phase 1 evidence (A2.2).
- **Not determinable, and what would settle it:** whether a real Pi agent would ever write into OMP at all — Pi ships no OMP client and no OMP-related MCP entry is active in the profile (A4, "Not determinable from evidence"). What answers it: the decision/config that gives Pi an `omp-mcp`/REST client; the safety analysis above then applies unchanged.

## What is NOT proposed

- Putting Pi's memory into the app's OMP instance (`:3456`). A4's verdict is "cannot share the instance safely as it stands", and none of its three conditions holds today. Nothing in this document proposes it.
- Reusing the app's credential or its namespace. `project:prompt-matrix` is a constant, carries no per-project identity, and the same key would grant list/get/put/delete over all 1160 app rows (A2.3, A4 verdict #2).
- Turning on Pi's native memory backends as the integration. `memory.backend` is `off` (`off`/`local`/`hindsight`/`mnemopi`/`sharpshooter`, `settings-schema.ts:3167-3179`); `mnemopi` is a local SQLite engine with its own MCP server that is installed but unreachable, `hindsight` needs a remote server at `hindsight.apiUrl`, and neither talks to OMP (A1.6, A4.2).
- Semantic retrieval. This build is keyword-only: `mode` is ignored and `mode_used` is hard-coded `'keyword'` (A2.4, A2.5; and the repo already bans claiming otherwise, `docs/anti-claims.md`).
- Treating `namespace` as a security boundary, or scoping reads by tag. Namespaces are filters that any key-holder can ignore (A4.4); `search.tags` is accepted and ignored (`types.js:27` vs `sqlite.js:159-181`).
- Any change to app code, app routes, or the box's units. This document is design; the app's `omp_client.py`, `routers/omp_routes.py`, `services/*` and `/etc/systemd/system/omp.service` are untouched by it.
- Installing Pi on the box. Pi is not present there and this design does not require it: the memory path is Pi (workstation) → OMP endpoint, not Pi-on-host (A1 §6).
